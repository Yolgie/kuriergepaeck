# KGP/1 proposed specification

## 1. Scope and trust

One ephemeral receiver R pairs with one source S for one explicitly approved
credential. The vault, master password and vault key remain exclusively on S.
The adapter MUST expose only the selected credential, never a remote search or bulk
export interface. Selection and approval are local operations, never relay commands.

Both endpoint implementations, their code distribution and OS/runtime are trusted.
The relay L is actively malicious: it can replace, reorder, replay, suppress or retain
all network traffic. TLS protects transport and routing capabilities from ordinary
network attackers; it does not authenticate a receiver key to S. S obtains that key
**only from the QR shown by R**. Neither a relay response nor a claimed hostname may
replace it. QR scanning authenticates a session key, not the receiver's legal name,
software integrity or persistent identity. The user must scan the intended screen.

The QR also contains a high-entropy secret. Anyone photographing it can race to act
as a source. Hide the QR after pairing; never upload it to a scanner service. This
is possession-based pairing, not authentication of an enrolled source. An attacker
substituting the entire physical QR can redirect the transfer; cryptography cannot
detect that without a separate trusted identity/proximity channel.

A relay-hosted browser application cannot meet confidentiality against its own
malicious publisher: the publisher can change the QR key, capture plaintext, or
exfiltrate via otherwise legitimate relay messages. See [deployment choices](research.md).
No key confirmation, non-extractable key, CSP or TLS fixes malicious authorized code.

## 2. Constants, encoding and limits

All integers are unsigned big-endian. `u8/u16/u32/u64` denote their byte widths.
`||` is concatenation; `H` is SHA-256; `ASCII` has no terminator. Byte lengths count
encoded bytes, not characters. Exact byte strings are authenticated; never parse
and reserialize before checking them. Reject trailing bytes, truncation, unknown
values, integer overflow and limits before allocation. No compression or fragmentation.

| Constant | v1 value |
| --- | --- |
| Wire version | u16 = 1 |
| Suite | u16 = 1: RFC 9180 PSK mode (0x01), DHKEM(P-256, HKDF-SHA256) 0x0010, HKDF-SHA256 0x0001, AES-128-GCM 0x0001 |
| Session ID `sid` | 32 independently random bytes from R's CSPRNG |
| QR PSK `p` | 32 independently random bytes from R's CSPRNG |
| R public key `pkR` | 65-byte SEC1 uncompressed P-256 point, prefix 04 |
| TTL | 120 seconds, fixed in v1 |
| Clock tolerance | 30 seconds, never an extension to a local monotonic deadline |
| QR decoded bytes | at most 512 |
| Credential JSON | 1–16,384 bytes |
| Ciphertext | 16–16,400 bytes (includes 16-byte GCM tag) |
| Relay frame body | at most 16,512 bytes |

Private keys and p are fresh each session, memory-only; no restore/resume across
reload, crash or restart. Public keys and encapsulations MUST receive RFC 9180
P-256 validation; reject infinity, off-curve, compressed or noncanonical points.
No raw ECDH output is an application key. Do not substitute handwritten HPKE.

## 3. Pairing QR

The QR text is `kgp:1:` followed by unpadded canonical base64url of `B || p`.
Reject whitespace, padding, non-URL alphabet, nonzero unused bits and alternate
encodings (decode then re-encode and compare). It is data, not a navigable web URL.

```
B = ASCII("KGPQ") || u16(1) || u16(1) || sid
    || u64(created) || u64(expires) || u16(origin_length) || origin || pkR
expires = created + 120
```

Times are Unix seconds. `origin` is 1–200 ASCII bytes: canonical HTTPS origin,
lowercase DNS A-label hostname, optional nondefault decimal port, no userinfo,
path, query, fragment or trailing slash. Default 443 MUST be omitted. v1 excludes
IP literals. Example `https://relay.example`. Scan never automatically authorizes
network access: S shows the origin and applies a locally configured relay allowlist
before connecting, preventing QR-triggered requests to arbitrary internal services.
Reject redirects, including same-host redirects, at the protocol transport layer.

R generates B and p locally and registers **only sid**, never B, p, pkR or a QR image
with L. S validates the whole QR, local policy, suite and time before connecting.
R stores the exact B locally and never accepts a replacement B from L.
No receiver name, requested entry name or destination website is authenticated by
v1; do not imply otherwise in approval UI.

## 4. Relay transport profile

All requests use HTTPS, no cookies, ambient credentials or referrer; responses use
`Cache-Control: no-store`. Paths use canonical unpadded base64url sid (43 chars).
CORS permits only configured independent receiver origins, never credentialed `*`.
S is a native client, not a cross-origin form. Bodies and authorization MUST NOT
enter access logs, tracing, crash reports or analytics.

| Operation | Request | Successful response |
| --- | --- | --- |
| Create | `POST /kgp/1/sessions`, body sid (32 bytes) | 201, random 32-byte receiver token r |
| Join | `POST /kgp/1/sessions/{sid}/join`, empty body | 201, random 32-byte source token s; first join wins |
| Send | `POST /kgp/1/sessions/{sid}/frames`, binary frame | 204 |
| Poll | `GET /kgp/1/sessions/{sid}/frames`, no body | 200, one binary peer frame; or 204, empty |
| Close | `DELETE /kgp/1/sessions/{sid}`, no body | 204 |

Use `Content-Type: application/octet-stream` for bodies. After create/join, use
`Authorization: Bearer <base64url(r or s)>` for all operations; no tokens in URLs.
Tokens are routing capabilities, not E2E keys or peer authentication. Create/join
are deliberately unauthenticated but rate limited. An attacker can win join or
invent frames and deny service; S/R never rely on the relay's role claims.
A create collision returns 409: R discards all session material and starts fresh.
The relay MUST NOT generate a replacement sid/key. No session enumeration endpoint.

An honest relay has a 120-second monotonic deadline starting at create, bounded
volatile storage and one pending frame per direction. It retains the last accepted
frame per direction for exact retries until close/expiry. Poll returns that frame
until replaced; clients recognize exact duplicates. Only the following progression
is accepted: S hello; R ready; S credential or cancel; R receipt or cancel.
R cancel is also allowed immediately after hello. Delete/expiry removes all
frames and tokens. Return 404 for unknown/closed/expired or invalid capability
without differentiating them; 409 for conflicting state, 413 for oversize, 429
with bounded retry delay for rate limits, 400 for bad framing, 426 for unsupported
transport version. These are **unauthenticated transport observations**, not peer
errors or proof of delivery/cancellation. Capacity limits/rate budgets are a deployment
policy that MUST be documented before a relay prototype; these MUST NOT extend TTL.

An honest relay enforces this state machine atomically; it does not decrypt frames:

| Relay state | Accepted new event | Next |
| --- | --- | --- |
| ABSENT | create unused sid | OPEN |
| OPEN | first join, issue source token | JOINED |
| JOINED | S hello seq0 | HELLO |
| HELLO | R ready seq0 | READY |
| HELLO | R cancel seq0 | CANCELLED |
| READY | S credential seq1 | SENT |
| READY | S cancel seq1 or R cancel seq1 | CANCELLED |
| SENT | R receipt seq1 | RECEIPTED |
| SENT | R cancel seq1 | CANCELLED |
| Any live state | DELETE or deadline | CLOSED |

Exact-byte send retries do not transition state; conflicting used slots fail 409.
RECEIPTED/CANCELLED retain only final cached opaque frames until deadline or DELETE
so a dropped response can be retried. They accept no new transcript. CLOSED has no
capabilities or payload and cannot be reopened; a new create must use fresh sid.
No relay state proves endpoint approval, acceptance or confidentiality.

Relays never see p, private keys or derived keys. They do see sid, IPs, timing,
lengths, public encapsulation and message kinds. Malicious relays can retain
ciphertext indefinitely; expiry promises endpoint acceptance limits, not remote erasure.

## 5. Frames and handshake

Every frame has this exact header and body:

```
header = ASCII("KGPF") || u16(1) || sid || u8(kind) || u8(seq)
frame  = header || [enc, only for kind=1] || u32(ciphertext_length) || ciphertext
```

`enc` is the RFC 9180 65-byte encapsulation. No optional fields. Header length is
40 bytes. Suite is fixed by QR/version, not negotiated in a frame.

| kind | Direction | seq | Plaintext |
| --- | --- | --- | --- |
| 1 hello | S → R | 0 | ASCII("kgp/1/source-ready") |
| 2 ready | R → S | 0 | ASCII("kgp/1/receiver-ready") |
| 3 credential | S → R | 1 | credential JSON (§6) |
| 4 receipt | R → S | 1 | ASCII("kgp/1/accepted") |
| 5 cancel | S → R | 1 | one byte reason |
| 5 cancel | R → S | 0 or 1 | one byte reason |

Reasons: 1 user cancellation, 2 local expiry, 3 local failure. No diagnostic strings.
R seq0 cancellation is an alternative to ready; R seq1 cancellation is an
alternative to receipt. S cancellation is an alternative to credential. There
are no further records. In particular no cancel/retry can encrypt a different
plaintext at a sequence already used.

### HPKE and transcript binding

1. Set `t = H(B)`, `info = ASCII("KGP/1 hpke") || t`,
   `psk_id = ASCII("KGP/1 pairing") || t`. All labels are exact case-sensitive ASCII.
2. S calls RFC 9180 `SetupPSKS(pkR, info, p, psk_id)` once, yielding `enc, ctxS`.
   R calls `SetupPSKR(enc, skR, info, p, psk_id)` once on receipt of hello.
   Follow RFC argument semantics if a library uses different parameter ordering.
3. S hello is `ctxS.Seal(header || enc, ASCII("kgp/1/source-ready"))`.
   R opens it with the same AAD and checks exact plaintext. The HPKE sequence is 0.
   Successful opening confirms QR-secret possession plus the selected encapsulation,
   **not an enrolled source identity**. R locks this context; never replace enc.
4. Let `c = H(B || enc || hello_ciphertext)`. Using each HPKE context's RFC 9180
   `Export(exporter_context, L)`, derive:
   `kr = Export(ASCII("KGP/1 r2s key") || c, 16)` and
   `nr = Export(ASCII("KGP/1 r2s nonce") || c, 12)`.
   These are the ONLY application exporter outputs. Do not expose exporter_secret.
5. R ready uses AES-128-GCM with key kr, 128-bit tag, nonce
   `nr XOR I2OSP(seq,12)` and AAD `header || c` (seq=0).
   S verifies exact plaintext before allowing approval/send. This confirms that the
   peer holds skR and p for this transcript; it cannot be a relay-substituted key.
6. S now displays the paired session/relay context and **exact fields of one locally
   selected credential**. Approval is bound to t, enc and an immutable snapshot of
   those field values. Any selection/field change invalidates approval. Do not allow
   approval solely from a remote request. Cancellation or expiry takes priority until
   the atomic send commitment. After explicit approval, S seals kind3 using ctxS
   at HPKE seq1 with AAD `header || c`. R opens with ctxR at seq1 and the same AAD.
   S cancel uses this same seq1 slot instead. Never share or reset HPKE contexts.
7. R atomically consumes the valid credential before exposing plaintext, then sends
   receipt at r2s seq1 using kr/nr and AAD `header || c`. A valid receipt confirms
   protocol acceptance, not reveal, copy, autofill or deletion. An R cancel uses
   the next unused r2s slot with the same AEAD/AAD rules.

RFC 9180 supplies DHKEM, labeled HKDF extraction/expansion, suite binding and the
S→R AEAD nonce schedule; this design adds no primitive or raw-ECDH key derivation.
The reverse record construction uses the usual sequence-XOR nonce convention with
a distinct exporter-derived key. The application labels, transcript composition
and state transitions still need review; an RFC does not certify this composition.

Never send credential data in hello, QR, URL, relay registration, error or headers.
Both directional record counters start at zero, never wrap, and permit at most two
records. GCM tags are appended to ciphertext as Web Crypto does. All lengths,
headers, sid, version, key, expiry, origin and suite are bound either through info
or AAD. A key from a new session cannot decrypt an old frame.

## 6. Provider-neutral credential envelope

Plaintext is strict UTF-8 JSON object with exactly `schema`, `username`, `password`:
`{"schema":"login/1","username":"synthetic-user","password":"dummy-only"}`.
Both fields are strings, may be empty, and are limited by total encoded byte size.
Reject duplicate keys (including escaped equivalents), unknown keys, non-string
values, malformed UTF-8, lone surrogates, nesting and trailing non-whitespace.
No Unicode normalization; preserve bytes/values selected by the user. JSON member
order and whitespace are not significant for parsing; AEAD covers original bytes.
No attachments, vault IDs, URL lists, TOTP seeds, executable data or arbitrary custom
fields in v1. New credential types require a new reviewed protocol profile/version.

The trusted source UI MUST offer field selection; unapproved username/password is
sent as an empty string, clearly shown in approval. One session never combines
entries. R renders values only as inert text, never HTML/URLs/scripts. No auto-submit
or autofill authorization is conveyed. Browser display is masked by default with
intentional reveal/copy and local cleanup; masking does not protect from scripts.

## 7. Endpoint state machines and races

All state transitions and deadline checks are serialized/atomic per session.
Outbound frames are encrypted exactly once then cached as immutable bytes; a retry
sends identical bytes. Exact duplicate peer frames have no effect and may trigger
resending the already cached next frame. A different frame for a used slot, wrong
sid/direction/kind/seq, malformed plaintext or failed authentication terminates locally
without plaintext exposure. Do not advance HPKE counters on transport duplicates.
An attacker can therefore cause denial of service, intentionally preferable to
replacing a key or trying alternate transcripts. There is no handshake retry with
new randomness in the same session.

| Source state | Event / action | Next |
| --- | --- | --- |
| IDLE | valid QR, policy/time check; join | CONNECTING |
| CONNECTING | join success; setup and cache/send hello | WAIT_READY |
| WAIT_READY | valid ready seq0 | WAIT_APPROVAL |
| WAIT_READY | valid R cancel seq0 | CANCELLED |
| WAIT_APPROVAL | explicit snapshot approval and valid deadline; atomically cache credential seq1, mark spent before send | WAIT_RECEIPT |
| WAIT_APPROVAL | local cancel; cache/send S cancel seq1 | CANCELLED |
| WAIT_APPROVAL | valid R cancel seq1 | CANCELLED |
| WAIT_RECEIPT | valid receipt seq1 | COMPLETE |
| WAIT_RECEIPT | R cancel, local timeout/cancel or transport failure | DELIVERY_UNKNOWN |

S may select an entry earlier but MUST approve the immutable snapshot after ready.
A user abort while WAIT_READY can only close locally (or delete relay session), not
forge a confirmed remote cancellation. Local expiry/error in any pre-send state is
terminal EXPIRED/FAILED. No error ever returns to IDLE with the old sid.

| Receiver state | Event / action | Next |
| --- | --- | --- |
| IDLE | generate secrets, create accepted, show QR | WAIT_HELLO |
| WAIT_HELLO | valid hello; lock context, hide QR, send ready seq0 | WAIT_CREDENTIAL |
| WAIT_HELLO | local cancel after valid hello but before ready; send R cancel seq0 | CANCELLED |
| WAIT_CREDENTIAL | valid S credential seq1, schema and deadline valid; atomically consume, send receipt seq1 | DISPLAY |
| WAIT_CREDENTIAL | valid S cancel seq1 | CANCELLED |
| WAIT_CREDENTIAL | local cancel; cache/send R cancel seq1 | CANCELLED |
| DISPLAY | user dismisses or deadline arrives | CLOSED |

Local cancel before a valid hello is local-only. All nonterminal states can expire
or fail locally. On expiry in DISPLAY remove UI plaintext and clipboard only if
platform policy permits without overwriting unrelated user clipboard contents;
never promise a remote or browser-memory wipe. DISPLAY can process exact credential
duplicates only to resend cached receipt, never reveal/copy or accept again.

Terminal states cannot reopen. Best-effort DELETE is advisory; receiver acceptance
and source single-send enforcement do not depend on honest relay deletion. Terminal
sessions drop keys/plaintext/QR and keep only cached encrypted receipt as needed
until the original deadline. After reload/crash, never reconstruct a session. New
pairing requires fresh sid, p and keys. No persistent replay database is necessary
because old keys cannot be restored. A malicious endpoint can retain plaintext;
this protocol cannot impose single use on compromised clients.

**Exactly once means at most one approved envelope and one receiver consumption.**
Network delivery cannot be guaranteed exactly once. After S commits ciphertext,
loss of receipt means DELIVERY_UNKNOWN, never "not delivered" or safe retry with
another credential. A new session needs new approval and warns that the old
credential may have arrived. Cancel/delete cannot revoke ciphertext already sent.
If receipt and cancel race, the first local atomic terminal transition wins;
neither outcome proves the other endpoint erased anything.

## 8. Expiration and errors

R sets a monotonic deadline at key generation +120 s, so relay/create delays reduce
usable time. Check wall time and monotonic time before every state change and before
exposing plaintext. S rejects QR when `created > now+30`, `expires <= now`, or
`expires-created !=120`. Its deadline is scan-monotonic-time + min(120, expires-now).
S also checks wall time `<expires` before committing. R never extends its original
deadline based on source clocks, relay responses, retries or activity. On suspension,
resume or clock rollback, fail closed if elapsed time cannot be established; use an
elapsed clock including sleep, or expire on resume. Modest skew can yield early
failure; it never authorizes receiver acceptance after its 120-second lifetime.

Unauthenticated input errors return generic failure locally, never a cryptographic
oracle detailing PSK/key/tag checks. No peer diagnostic plaintext before handshake.
A client may send authenticated cancel only in an unused allowed slot; otherwise
close locally. Limit failure handling to one attempt, no automatic crypto fallback.
HTTP failures may retry only identical cached requests/frames before deadline;
ambiguous create/join failure aborts because no idempotent capability recovery is
specified. Retry backoff must be bounded by remaining time. Never retry a credential
with altered values or restart a counter. Source UI distinguishes expired, cancelled,
failed and delivery-unknown without relying on relay text.

## 9. Versioning and compatibility

Protocol version, suite and credential schema are separate from relay, adapter and
UI release numbers. KGP/1 has exactly one suite and one schema; there is no unauthenticated
algorithm negotiation. QR version, B version, URI version, HTTP path and frame version
MUST agree. Unsupported versions fail before joining/sending secrets; never fall back
automatically. Upgrading/changing protocol requires a fresh QR and user approval.

Component minor upgrades MUST preserve all v1 byte formats and rejection behavior.
No extension/unknown-field ignoring in v1. New optional UI/local functionality can
change independently, but changes to cryptographic inputs, wire fields, TTL, schema
or authentication require a new protocol version and compatibility review. Future
multi-version offers need downgrade-resistant transcript binding; not specified here.
A relay can host /kgp/1 and a future version concurrently with independent sessions.
Support windows are a release policy still to decide, not a silent protocol fallback.
